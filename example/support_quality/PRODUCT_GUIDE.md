# 产品理解：工单质量分析助手

本说明先讲产品，再讲技术。当前项目基于 OpenChatBI，不是此前已清除的学习陪练。
这是本机可演示的改进版，不是已经部署到企业、使用真实公司数据的产品。

## 1. 一句话定位

让不写 SQL 的客服/运营主管，用日常语言核对业务数据，继续追问细分结果，并查到计算规则和出处。

当前用“客服工单”作为具体场景：用户反馈一个问题，就形成一条待跟踪的记录。
例如账号登录失败、账单疑问、配送问题。分析的是处理情况，不负责代替客服解决这些问题。
account / billing / delivery 分别是演示用的账号、账务、配送类别。

## 2. 为什么会有需求

主管希望知道某段时间收到多少问题、超时多少、主要集中在哪类、比例怎么算。
不写 SQL 时，可以请数据同事查询、导出表格计算，或看已有报表。这些方式本身都合理。
问题是临时追问需要改查询，且“超时率”未必人人按同一种规则理解。

例如，未解决但已经过截止时间的工单算不算超时？测试工单算不算？
如果直接让模型自由写 SQL，可能语法正确、查到数字，但用错了分母。

本项目围绕三件事做闭环：自然语言提问、按统一规则取数、把依据交给用户核对。
如果需求永远只有三个固定数字，普通报表更直接，并不需要为使用 Agent 而使用 Agent。
Agent 在这里的价值主要是语言理解、连续追问、规则查询、任务委派和信息补充。

## 3. 一次完整的用户流程

### 第一步：查看整体情况

输入：统计 2026-10-01（含）到 2026-10-08（不含）新建工单的超时率，使用 UTC，按整体统计，不筛选类别。

返回：40%（4/10）。含义是本次范围/口径内有 10 条有效工单，其中 4 条超时。
这不是模型对服务质量打了 40 分，也不是某家公司的实际统计。
数据库共有 15 条自编记录；测试、重复、观察截止前取消及时间范围外的记录不是全部进入分母。

日期包含 10 月 1 日零点，不包含 10 月 8 日零点。这样相邻区间不会重复计数边界记录。
本案例固定按 10 月 8 日零点前已观察到的情况判断，不是按今天重新判断历史超时。

### 第二步：追问具体类别

输入：保持刚才日期和口径，按类别拆开看。

| 类别 | 有效数量 | 超时数量 | 超时率 |
| --- | --- | --- | --- |
| account，账号类 | 4 | 3 | 75% |
| billing，账务类 | 2 | 0 | 0% |
| delivery，配送类 | 4 | 1 | 25% |
| 整体 | 10 | 4 | 40% |

系统需要从当前对话拿回上轮日期和指标，再把分组方式改为 category。
整体比例是 (3+0+1)/(4+2+4)，不是把 75%、0%、25% 直接平均。
账号类值得进一步检查，但样本少、字段有限，不能据此断言某个人失职或自动得出根因。

### 第三步：查统计规则

输入：超时率分母包括未解决的工单吗？请查规则，给出规则出处和 chunk_id。

系统检索项目自编的 METRICS.md，返回相关规则片段及来源。
本版分母包括所有有效工单，包括未解决及尚未到处理期限的记录。
超时分子包含截止前已逾期但还没解决的记录，以及已观察到的晚于期限解决记录。
规则是我们为演示明确制定的口径，不是行业唯一标准，也不是模型临时决定的规则。

support-quality-v1 是规则版本，overdue-rate 是其中的章节，chunk_id 用来标识检索片段。
这些标识方便追溯，不是来源真实性的安全认证，也不是模型置信分数。
当前答案采用检索原文展示，不再让小模型额外自由改写，以免引入相反结论。

### 第四步：信息不足时补充

新建对话后输入“统计超时率”，没有提供日期。
缺少的必填参数若为 null，会被程序拦住，进入 AskHuman 暂停，让用户补充。
用户补齐范围后，原 checkpoint 恢复并继续处理；不是把整个流程从头重新来。

“这周”不是“沿用刚才的日期”。它是新的相对时间条件，需要参考当前日期、时区和周的定义。
本演示版暂不自动换算“这周/上周/今天”等相对时间；当前提问没有完整明确 ISO 日期范围时，
程序先要求确认 UTC 起止日期，并说明合成数据只观察到哪个截止点，而不是把旧日期改名为本周。
没有本轮工具执行时，也不能仅凭历史答案返回新的统计或规则结论。

注意：保护能发现缺失/非法参数，不等于已经证明模型永远不猜测用户意图。
例如一句“看看质量”本应进一步澄清指标；模型若擅自填入合法指标，单靠类型校验无法判断其是否符合原意。

### 第五步：原始数据核对

输入：请查询合成工单原始表中的最大 id，包括测试、重复、已取消记录，不作业务排除、不限制日期。给出真实 SQL 和查询结果，不要图表。

这是原始审计请求，不是三个业务指标之一，不能套用有效工单排除规则。
主助手把任务交给原 Text2SQL 子流程，读取表结构、形成查询、执行只读 SQL。
已验证结果是 SELECT max(id) AS max_id FROM support_tickets，max_id=15。
这个示例用于核对另一条执行路径；MAX(id) 不是普遍适用的总行数算法。

## 4. 系统内部谁负责什么

统计路径：

用户提问 -> 程序缩小工具范围 -> 模型填写指标/日期等参数 -> 程序检查 ->
support_quality 按固定参数化 SQL 查库 -> 程序根据实际结果展示答案和依据。

规则路径：

用户问定义 -> 检索规则文档 -> 返回相关片段/出处 -> 程序展示原文。

原始审计路径：

用户问原始记录 -> 主助手委派 -> 原 SQL 子流程查表结构/生成 SQL/执行 -> 展示真实 SQL 和结果。

模型负责把语言映射到结构化请求；数据库保存记录；普通代码负责计算、校验和执行。
不是模型直接操作屏幕，也不是模型心算百分比。
部分路由、必选工具和最终报告由代码约束，不应说成全部由模型自主规划。

## 5. 为什么有两条查数路径

固定指标需要稳定口径，所以用参数化工具执行；模型不能随意改变分母。
原始审计有不同的请求范围，所以走 Text2SQL，但也更需要控制执行权限和核验结果。

两条路径不是重复：一条优先统一业务定义，一条允许核对约定表里的原始事实。
当前演示使用只读 SQLite，不是 MySQL；数据库性能/事务/Redis 等由另一 Java 项目重点承担。

## 6. 技术名词对应到产品行为

| 名词 | 在这个产品中指什么 | 当前边界 |
| --- | --- | --- |
| LLM，大语言模型 | 理解自然语言、结合本轮上下文填参数、提出工具调用 | 不保证所有表达都能正确理解 |
| Tool Calling，工具调用 | 模型给出工具名和参数，程序校验后执行 | 不是模型直接获得数据库任意操作权 |
| Skill，任务技能 | 三指标的说明、输入、规则、执行工具、输出约定 | 固定预设任务，不是动态插件市场 |
| RAG，检索增强 | 回答规则前，先从资料中检索相关片段 | 默认 BM25 词项检索；向量模式另有真实本机验证，当前页面未启用 |
| LangChain | 统一模型接口、消息和工具描述等组件 | 复用依赖，不是自行实现模型框架 |
| LangGraph | 按状态组织模型、工具、暂停/恢复和子流程 | 主图/SQL 子图主要由上游提供 |
| ReAct | 根据已有结果决定后续动作的思路 | 原主图有模型/工具循环；演示受程序路由约束，不是纯自主循环 |
| 小规模角色协作 | 主助手处理对话，SQL 角色处理查询子任务 | 可使用同一个模型；不是每个问题都启动多个 Agent |
| Context，上下文 | 当前会话已有问题、时间和工具结果 | 简单会话上下文不是跨用户长期记忆 |
| Checkpoint，检查点 | 保存执行状态，切回后恢复待补充任务 | 不代表任意故障都能自动恢复 |
| Harness，运行支撑与约束 | 工具范围、参数校验、只读数据、失败状态和轨迹 | 不是完整安全沙箱或全应用费用/超时体系 |

ReAct 不是 React；后者是前端框架。当前页面用的是 Streamlit，不是 React。
Ollama 当前通过本机 HTTP 接口供模型调用；本地模型也有 API，只是不用付费公网模型 API。

## 7. 页面怎么理解

- 中间消息区：用户的问题、结果和计算/来源依据。
- 底部输入框：输入新问题或当前任务需要补充的信息。
- 执行过程：工具执行与部分模型输出的中文展示，不是完整或经过保证的模型内部思维。
- 用户标识：演示用的会话归属标识，不是正式登录认证；改它不能证明已有多租户权限隔离。
- 会话编号：某一段对话的编号；相同用户/会话编号可恢复对应历史。
- 新建对话：换一个会话编号，不继承旧条件，也不删除旧记录。
- 历史对话：按首个问题显示标题，点击即可返回；从已有 checkpoint 读取最近 50 段，不另建历史数据库。刷新后仍保留，尚未提问的空白对话不列入。
- 报告文件：继承自上游的入口，暂无文件时明确显示空状态；不代表本轮已验收报告生成、图表或生产部署。操作标签已中文化，SQL/表名/引用编号和原文不伪造翻译。

## 8. 原版和自己的改进

原版提供了模型/工具主图、SQL 子流程、checkpoint 和 Streamlit 页面。
我们加入具体合成场景、三指标契约/Skill、业务规则检索与引用、任务工具范围约束、
真实结果展示、原始审计范围保护，以及针对这些变化的测试和前端会话/恢复修复。

贡献的关键问题是“如何减少口径漂移和无依据回答”，不是换一个页面标题或冒充从零造平台。
安装依赖和启动服务只是准备工作，不是核心项目创新。

## 9. 产品当前边界

当前支持三指标、约定单表、整体/分类统计、规则查阅、原始只读查询和缺参暂停恢复。
不提供任意文件上传、工单创建/派单、退款执行、业务根因保证或生产级权限。
没有匹配资料不能猜；没有数据不是 0%；数据库失败不是没有数据；未执行 SQL 不是查询成功。
真实本机小案例通过不等于任意模型、任意数据、付费 API 或生产质量已验收。

## 10. 接下来的学习顺序

先确认自己能用产品语言说清：谁用、输入什么、输出什么、如何核对、什么情况下不能回答。
再只跟一条请求学习：网页输入 -> 模型参数 -> 工具执行 -> 数据库结果 -> 页面显示。
之后分别学习规则检索、连续对话、AskHuman/checkpoint、SQL 角色协作和测试。
不要求一次理解所有术语，也不在未经用户确认时记录为“已经掌握”。
