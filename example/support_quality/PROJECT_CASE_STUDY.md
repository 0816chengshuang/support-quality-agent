# 项目陈述：工单质量分析助手

## 项目定位

这是基于 [OpenChatBI](https://github.com/zhongyu09/openchatbi) 的 Agent 应用改进案例。场景是客服或运营主管用自然语言核对工单数量、超时率与处理时长，连续追问分类结果，并查到指标定义的出处。当前数据完全合成；项目展示的是如何把模型、工具、规则资料和可核对的结果接成一条小型工作流，不是企业部署或大数据性能项目。

固定报表足以回答预先确定的几个数字。这里使用 Agent 的理由是用户还会临时改变范围、追问口径、缺少条件或要求原始记录核对；系统必须在不同任务间选择工具，并在没有依据时停下来。

## 一套可以操作的演示

在 [本机页面](http://127.0.0.1:8501/)新建对话，按顺序输入：

1. `统计 2026-10-01（含）到 2026-10-08（不含）新建工单的超时率，使用 UTC，按整体统计，不筛类别。` 指标工具按固定口径返回 40%（4/10），同时给出日期、观察截止、分子/分母与规则版本。
2. `保持刚才日期和口径，按类别拆开看。` 会话状态保留条件，结果为 account 3/4、billing 0/2、delivery 1/4。结果由数据库计算，不是模型编的数字。
3. `超时率分母包括未解决工单吗？请查规则并给出处。` 检索 `METRICS.md` 的相关片段，展示 `source_ref` 与 `chunk_id`。当前页面默认 BM25；单独验证过本地向量模式，但不声称页面默认使用向量检索。
4. `请查询合成工单原始表中的最大 id，包括测试、重复、已取消记录，不作业务排除、不限制日期。给出真实 SQL 和查询结果，不要图表。` 主助手把原始查询交给上游 Text2SQL 子图，实际执行只读 `SELECT max(id) AS max_id FROM support_tickets`，显示 15 与 SQL/CSV。`MAX(id)` 只是这次审计请求，不是通用行数算法。
5. 再新建对话，问 `统计超时率`。缺少时间范围时应先询问；补充完整日期后从保存的任务状态继续。旧会话可以从左侧历史列表返回。

这些步骤各有现有运行记录；不要把它们写成一次模型独立规划的长任务。页面执行过程能看到工具步骤和实际结果，内部状态、源码贡献与离线验证由下表说明。

## 原版能力与本地改进

| 部分 | 来源与作用 |
| --- | --- |
| 主 LangGraph、Text2SQL 子图、ToolNode、AskHuman、checkpoint、Streamlit 入口 | OpenChatBI 上游提供。主助手交给 SQL 子图属于已有的有限角色协作。 |
| `support_quality` Skill | 本地增加三项指标的输入约束、统一口径、参数化只读 SQL、空数据及越界状态；模型只填参数。 |
| 业务规则检索 | 本地在已有 `search_knowledge` 工具中加入 Markdown 分段、BM25/可选向量检索、来源与内容版本、上下文预算；页面显示检索原文，避免小模型改写出相反结论。 |
| 请求与证据约束 | 本地缩小可用工具、核验日期和范围、避免把指标排除规则套到原始审计；没有本轮真实工具结果时不把旧答案当新结果。 |
| 会话和页面 | 本地修复新建对话后找回历史、待补充任务恢复、非流式报告展示及中文操作标签。 |

这里的 Skill 是一个预先定义的任务能力；它不是动态插件系统。关键词路由与程序生成的报告不是模型自主规划。指标统计只调用一个工具，不能称作多 Agent；原始 SQL 才出现主助手到 SQL 专项子图的交接，而且子图仍主要是上游实现。

## 对应的 Agent 基础

| 知识点 | 本项目能实际讲清什么 | 不能声称什么 |
| --- | --- | --- |
| 模型与 Tool Calling | 模型通过本机 OpenAI 兼容接口提出结构化工具调用；程序校验并执行；观察参数错误和失败状态。 | 任意模型或付费平台上的完整流程都通过。 |
| 检索增强 | 资料分段、BM25 默认检索、top-k/上下文预算、来源引用；本地 embedding 向量模式有单独小样本验证。 | 大规模 RAG 召回、经评估的自由生成答案或页面默认向量检索。 |
| Skill | 明确适用任务、输入、计算规则和输出证据，把易漂移的业务口径固定下来。 | 自动发现和组合任意 Skill。 |
| 工作流与 ReAct | 上游图在模型与工具之间循环；本地增加任务范围和证据约束，能对比由模型决定与由程序保证的环节。 | 全自主规划或自研 LangGraph 框架。 |
| 角色协作 | 原始审计中主助手交给 Text2SQL 子图，子图提取信息、选表、生成并执行 SQL。 | 每条问题都走多个 Agent，或本地从零构建了完整多 Agent 系统。 |
| 上下文与 Harness | 旧会话恢复、缺参暂停/继续、工具白名单、有限重试、只读连接、结果校验。 | 生产权限隔离、完整 SQL 沙箱、全局费用/时延控制或已验证的长对话压缩。 |
| 评估 | 固定正常/歧义/缺资料/原始审计案例、离线回归，以及浏览器真实本机模型检查。 | 生产准确率、性能吞吐或跨模型稳定性。 |

## 可核对的证据与限制

- 本机生成的 `.run/browser-acceptance.md`：原页面和真实本机模型完成整体、分类、规则引用、追问恢复与 SQL 审计。用户后续还发现并推动修复了“这周”误套旧日期的问题；见 `.run/zh-history-acceptance.md`。
- 本机生成的 `.run/local-retrieval-smoke.json`：六个资料问题的 Top-3 均包含预期章节，Top-1 为五个。样本极小，不能用作生产召回率。
- 本机生成的 `.run/local-graph-vector.json`：一次真实本机聊天模型和本地 embedding 的规则检索案例通过；默认演示仍用 BM25。
- 本机生成的 `.run/baseline.xml`：整理后重跑 360 项通过（22.10 秒）。离线测试含替身，不能当作真实模型质量证据。
- `.run/local-graph-configured.json` 当前文件后来被四场景局部回放覆盖，状态为 `not_completed`；历史“十步通过”的陈述没有现存同名文件可独立复核，本项目陈述不引用它作为当前通过证据。
- 数据只有 15 条刻意设计的边界样本，适合验证超时、取消、重复、测试与观察截止，不支持统计显著性或性能结论。项目不宣称线上用户、真实业务收益或生产权限。此前付费平台只验证过部分调用，完整 SQL 路径未通过；当前演示用免费本机模型。

`.run/` 是忽略的本机运行产物，不随 Git 仓库提交。别人复现时先依照 [场景说明](./README.md)准备本地环境，再运行 `scripts/test-baseline.ps1` 或对应的本地回放命令；无法取得这里提到的历史浏览器记录时，不把它们当作公开仓库自带的证明。

## 可写进项目经历的表述

> 基于 OpenChatBI 的 LangGraph 工作流，面向合成工单场景改进自然语言质量分析：设计三指标 Skill 与参数化只读查询，约束日期、分组及证据展示，避免模型直接改写指标分母。

> 在现有知识检索工具中增加业务文档分块、BM25/可选本地向量检索、来源引用和上下文预算；针对缺资料与错误引用保留明确失败状态，并用小样本验证真实本地向量路径。

> 复用上游 Text2SQL 专项子图与 checkpoint，修复原始审计范围被指标规则污染、相对时间误用旧结果以及前端会话恢复问题；通过离线回归和本机网页案例核对实际 SQL、统计值与引用来源。

面试时应先说清楚“基于开源项目改进”，再讲自己发现的错误、如何约束模型与工具、哪些行为由上游提供。不要把 15 条样本、六个检索问题或 360 个离线测试包装成生产效果，也不要自称实现了通用多 Agent 平台。

## 收敛决定

以上能力可以支撑一份**边界清楚的 Agent 基础项目经历**，网页不需要把每个内部节点做成按钮。当前停止为覆盖术语而增加新 Agent、图表或大数据功能；后续只有实际演示问题或真实测试失败才继续改代码。这里的“停止功能扩展”不等于生产验收、用户已经掌握知识点或已完成另一 Java 后端项目。
